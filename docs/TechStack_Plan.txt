## Context

This project follows earlier work on passive OS fingerprinting: Qiskit-based quantum classifiers and a classical XGBoost baseline (separate, unpublished projects). QuantumNeuralNetworkOS is the PennyLane-based successor: a hybrid quantum-classical neural network that classifies operating systems from network packet features (nPrint format), using PyTorch integration and GPU-accelerated quantum simulation via Docker.

PennyLane was chosen over the existing Qiskit stack for: automatic differentiation (Adam/SGD vs COBYLA), native PyTorch integration via TorchLayer, write-once backend portability, and mini-batch training via DataLoader.

---

## Design Principle: Classical/Quantum Separation

All data processing and transformation is done classically. The quantum circuit only handles model generation.

### Classical Compute (data)
- nPrint CSV ingestion (962 columns: 961 ternary features (-1/0/1) + 1 label)
- Column removal (src_ip, IPv4 src/dst/identification, TCP ports, seq/ack numbers — same indices as the XGBoost baseline)
- Feature selection (SelectKBest with mutual_info_classif, k=20; since
  2026-07-27 the production model instead takes an explicit XGBoost
  gain-ranked top-20 list via --feature-names — see DECISIONS.txt Decision 9)
- Label encoding (LabelEncoder)
- Stratified train/test splitting (80/20)
- Batching via PyTorch DataLoader (batch_size=512, 4 workers, pinned memory)

### Quantum Compute (model)
- Receives clean tensor of shape (batch_size, 20)
- RY AngleEmbedding into 20-qubit circuit, angle (input + 1) * pi/2 (ternary-aware; see Feature Encoding below)
- Ring topology entangler (nearest-neighbor + wrap-around) after encoding: fixed CNOT (default), trainable CRZ (--entangler crz), or CNOT ring plus long-range shortcuts at offsets 5 and 10 (--entangler ring_long — the production model)
- 4 variational layers with data re-uploading (AngleEmbedding + per-qubit RY + RZ rotations + ring entangler)
- Pauli expectation values on all 20 qubits: Z+X+Y (60 outputs, default) or Z only (20 outputs, --measure-axes Z — the production model; DECISIONS.txt Decision 8)
- Classical head maps quantum expvals and/or raw features to class logits: [BatchNorm1d?] -> Linear(head_in,128) -> ReLU -> Dropout(p) -> Linear(128,n_classes); head_in is 60 (quantum, Z+X+Y), 80 (+--skip), 40 (Z-only + --skip, the production model), or 20 (--no-quantum --skip classical baseline)
- Training via Adam + FocalLoss (class-weighted, gamma=2.0) + adjoint differentiation backprop

The quantum side has no knowledge of nPrint, CSV formats, or feature engineering. It takes a preprocessed feature tensor and learns to classify.

## Qubit Count

Using 20 features (SelectKBest, or an explicit --feature-names list) with AngleEmbedding (1 feature = 1 qubit):

- **20 qubits**
- State vector: 2^20 amplitudes x 16 bytes (complex128) = **16 MB**
- Well within the 24 GB VRAM of the RTX 3090

Reference table:

Qubits | Amplitudes | State vector size
------ | ---------- | -----------------
20     | 1M         | 16 MB
25     | 33M        | 512 MB
30     | 1B         | 16 GB (fills RTX 3090)
33     | 8.6B       | 128 GB
40     | 1T         | 16 TB

At 20 qubits, GPU acceleration provides modest benefit — the circuit is too small to saturate the RTX 3090's 10,496 CUDA cores. The GPU helps with parallel gate operations during adjoint differentiation, but per-batch speedup over lightning.qubit (CPU) is marginal. GPU becomes essential at ~28+ qubits where the state vector exceeds CPU cache sizes.

## Quantum Circuit Architecture

### Feature Encoding

The circuit uses ternary nPrint features (-1 = field absent, 0 = bit clear, 1 = bit set). No normalization is needed — features are encoded as RY((feature + 1) * pi/2), so -1 maps to |0>, 0 maps to the Bloch equator (equal superposition), and 1 maps to |1>.

IMPORTANT (2026-07-15, see DECISIONS.txt Decision 6): the original RY(feature * pi) encoding silently aliased -1 with +1 — RY(-pi) = -RY(pi), identical up to global phase — so "field absent" and "bit set" entered the circuit as the same physical state (58% of selected-feature values are -1). The (x+1)*pi/2 encoding gives all three values distinct, measurable states.

Encoding         | PennyLane Op         | Qubits | Features
---------------- | -------------------- | ------ | --------
AngleEmbedding   | qml.AngleEmbedding   | 20     | 20 (one RY rotation per qubit)

### Entanglement After Encoding

Ring topology CNOT: qubit i→(i+1) % n_qubits for all i. Creates nearest-neighbor entanglement with wrap-around, allowing correlations between adjacent features to propagate through the ring.

Note: under the ternary encoding, 0-valued features sit on the Bloch equator
(superposition), so the first (post-encoding) ring genuinely entangles whenever
any feature is 0 — for typical packets, that is most of them. (Under the old
binary encoding the post-encoding state was a computational basis state and the
first ring was only a classical XOR permutation; that caveat no longer applies.)

Previously:
- Run 1-2: linear CNOT chain (q0→q1→q2→...→q19), nearest-neighbor only.
- Run 3: star topology from q0 (q0→q1, q0→q2, ..., q0→q19). Enabled long-range correlations via q0 hub but prevented direct qubit-to-qubit interaction (qubits 1-19 never directly entangled with each other).
- Run 4: ring topology. Changed because star topology created a bottleneck -- if features at qubit 8 and qubit 14 together distinguish windows-10-pro from windows-10, star topology cannot learn that correlation directly. Ring allows neighbor correlations to propagate while costing only 1 extra CNOT per layer vs star (20 vs 19).
- Run 6: configurable entangler. ENTANGLER / --entangler selects "cnot" (fixed ring, default) or "crz" (trainable controlled-RZ ring). CRZ(theta) has a learned angle per pair -- CRZ(0)=identity, larger angles couple more strongly -- so the model learns how much to entangle each neighboring pair instead of the fixed all-or-nothing CNOT. Adds one param/qubit/layer; "crz" checkpoints are not weight-compatible with "cnot".
- Run 7 (2026-07-24, DECISIONS.txt Decision 7): "ring_long" -- the fixed CNOT ring plus long-range CNOT shortcuts i→(i+5) and i→(i+10) mod 20 after every layer (--shortcut-offsets 5 10), so distant qubits interact within one layer instead of propagating around the ring. Same weight shapes as "cnot". Used by the production model.

### Variational Ansatz

Custom ansatz with data re-uploading (not BasicEntanglerLayers). Per layer:
1. Data re-upload: AngleEmbedding((inputs + 1) * pi/2) re-encodes the raw features (enables universal approximation)
2. RY(theta) and RZ(phi) on each qubit (2 parameters per qubit per layer)
3. Ring entangler for entanglement: fixed CNOT (default), trainable CRZ (--entangler crz, +1 param/qubit/layer), or CNOT ring + long-range shortcuts (--entangler ring_long)

Previously (Run 1-2): no data re-uploading, linear CNOT chain. Changed in Run 3 — re-uploading breaks the expressivity ceiling that caused both runs to plateau. (Earlier drafts of this doc described a "star topology CNOT from q0" here; the code has used the ring entangler since Run 4.)

Ansatz              | Params per layer | Total params (4 layers, 20 qubits) | Notes
------------------- | ---------------- | ----------------------------------- | -----
RY+RZ + CNOT ring   | 40               | 160                                 | Default; fixed entangler, 2 trainable rotations/qubit
RY+RZ + CRZ ring    | 60               | 240                                 | Run 6 --entangler crz; adds a learned coupling angle/qubit/layer
RY+RZ + ring_long   | 40               | 160                                 | Run 7 --entangler ring_long; CNOT ring + shortcuts at offsets 5,10; weight-compatible with cnot

This is more expressive than the BasicEntanglerLayers originally planned. RY handles amplitude control, RZ handles phase control, and the entangling ring correlates qubits — giving the ansatz access to a larger portion of the Hilbert space. With "crz" the coupling strength of each ring bond is itself trainable.

### Measurement

Default: return qml.expval(PauliZ(i)), qml.expval(PauliX(i)), qml.expval(PauliY(i)) for all 20 qubits. Output: 60 real values in [-1, 1].

Production (since Run 7, DECISIONS.txt Decision 8): --measure-axes Z, 20 outputs. Adjoint differentiation re-runs its reverse sweep once per observable, so the 60-observable default tripled the per-batch gradient cost; dropping X/Y roughly halved epoch time (~33 h -> ~17.7 h). The "zero additional gate cost" argument below is true of gates but not of gradients.

Previously (Run 1-3): PauliZ only (20 outputs). Changed in Run 4 — PauliZ measures one "axis" of information per qubit. Adding PauliX and PauliY extracts two additional orthogonal axes, giving the classical head 3x more signal with zero additional gate cost. The quantum state already contains this information; we were simply not reading it.

### Differentiation

diff_method is backend-dependent:
- default.qubit: backprop (exact, fast for small circuits)
- lightning.qubit / lightning.gpu: adjoint (memory-efficient, O(1) auxiliary state vectors)

### Circuit Definition (circuits/model.py)

Single file containing the create_circuit() factory function. Returns a QNode with torch interface and a weight_shapes dict for TorchLayer integration.

weight_shapes = {"weights": (n_layers, n_qubits, 2)}  # (4, 20, 2) = 160 params (cnot)
# With --entangler crz: (n_layers, n_qubits, 3) = (4, 20, 3) = 240 params
# With --entangler ring_long: same (4, 20, 2) shapes as cnot

## Data Pipeline (Classical Only)

Consumes nPrint CSV output (962 columns, last column = label).

1. Column removal    -- identifier-column index ranges centralized in config/defaults.py (kept identical to the XGBoost baseline so results are comparable)
2. Feature selection -- SelectKBest(mutual_info_classif, k=20), fitted on training set only (no data leakage)
3. Label encoding    -- LabelEncoder
4. Train/test split  -- stratified 80/20 split (random_state=42)
5. Batching          -- PyTorch DataLoader (batch_size=512, num_workers=4, pin_memory=True, persistent_workers=True)

No normalization: nPrint features are ternary (-1/0/1), encoded directly as RY((feature + 1) * pi/2).

Output: tensors of shape (batch_size, 20) for features, (batch_size,) for labels.

### Column Removal Ranges

Removes the src_ip column, IPv4 source/destination addresses and identification field, TCP ports, and sequence/acknowledgment numbers to prevent the classifier from memorizing network-specific identifiers:

- Column 0 (src_ip string column prepended by the capture tooling)
- Columns 97-129 (IPv4 src)
- Columns 130-160 (IPv4 dst)
- Columns 33-48 (IPv4 identification)
- Columns 480-512 (TCP src/dst ports)
- Columns 512-544 (TCP seq numbers)
- Columns 544-576 (TCP ack numbers)

Source of truth: COLUMNS_TO_REMOVE in config/defaults.py.

## Training Architecture (Quantum)

### Hybrid Model (HybridQuantumNet)

Input (20) -> [TorchLayer(QNode) -> 60 (Z+X+Y) or 20 (Z-only) expvals] and/or [raw 20 features] -> [BatchNorm1d?] -> Linear(head_in, 128) -> ReLU -> Dropout(p) -> Linear(128, n_classes) -> logits

qml.qnn.TorchLayer wraps the QNode as a standard nn.Module, so PyTorch handles all gradient computation automatically via adjoint differentiation on the quantum side and standard autograd on the classical side.

Previously (Run 1-3): 20 PauliZ outputs -> Linear(20, 64) -> ReLU -> Linear(64, 12). Changed in Run 4 to handle 60 measurement outputs and provide more capacity for fine-grained class discrimination. Dropout(0.3) prevents overfitting with the larger head.

Run 6 made the head composable (all flags persisted in the model config so test.py / --resume rebuild the same head; defaults reproduce Run 4/5 behavior):
- --batchnorm: BatchNorm1d on the head inputs. The 60 expvals span very different scales (PauliZ spread across [-1, 1], PauliX/Y clustered near 0), which conditions the first Linear poorly; per-feature BatchNorm across the batch fixes that (LayerNorm, per-sample, would not).
- --skip: concat the raw 20 features with the expvals (head_in 60 -> 80, or 20 -> 40 with Z-only measurement). Residual path so the head can use data the circuit maps poorly; provably >= a classical MLP on the raw features, and a built-in diagnostic (skip-column vs quantum-column weight norms) for how much the circuit is used.
- --dropout P: configurable (default 0.3). Lower to ~0.1 when the model is underfitting (train/val F1 track closely).
- --no-quantum (requires --skip): drops the circuit entirely -> classical baseline (raw 20 -> head). Isolates the circuit's marginal contribution; runs in seconds on CPU.

### Parameter Count

Default head (Run 4/5 defaults, cnot entangler):

Component        | Parameters
---------------- | ----------
Quantum layer    | 160 (4 layers x 20 qubits x 2 rotations; 240 with --entangler crz)
Linear(60, 128)  | 7,808 (60*128 + 128 bias)
Dropout(0.3)     | 0
Linear(128, 12)  | 1,548 (128*12 + 12 bias)
**Total**        | **9,516**

Variant head input dims: 60 (quantum only), 80 (--skip), 40 (Z-only + --skip, production), 20 (--no-quantum --skip). --batchnorm adds 2*head_in affine params. Changing head_in changes the Linear shapes, so variant checkpoints are not weight-compatible with the default -- use distinct model names when A/B-ing.

### Training Config

Setting              | Value                            | Reason
-------------------- | -------------------------------- | ------
Ansatz               | Custom RY+RZ (n_layers=4)        | More expressive than BasicEntanglerLayers
Optimizer            | Adam (lr=0.005)                  | Gradient-based, works with adjoint diff
LR warmup            | 3 epochs (lr/10 -> lr)           | Prevents large destructive updates before model finds a stable basin
LR scheduler         | ReduceLROnPlateau(0.5, patience=5) | Halves LR when val_f1 stalls for 5 epochs
LR floor             | 1e-5                             | Prevents LR from decaying to zero
Gradient clipping    | max_norm=0.75                    | Caps gradient magnitude; middle ground between 0.5 (starved gradients) and 1.0 (allowed collapses)
Loss                 | FocalLoss (class-weighted, gamma=2.0) | Focal modulation focuses gradients on hard/confusable examples; inverse-frequency weights handle class imbalance (implemented Run 5+; Runs 1-3 used CrossEntropyLoss, Run 4 used FocalLoss but with bad features)
Batch size           | 512                              | 8x reduction in batches per epoch vs original 64
Early stopping       | patience=10 on val F1            | Stops training when model plateaus
Checkpointing        | Best model per epoch (by val F1) | Saves .pt weights + .json config
Backend              | lightning.gpu (RTX 3090)         | Adjoint differentiation on GPU

### Focal Loss with Class Weights

Loss function: FocalLoss(weight=class_weights, gamma=2.0)
  FL(p_t) = -alpha_t * (1 - p_t)^gamma * log(p_t)

Class weights use inverse-frequency weighting: weight_i = (1 / count_i) normalized so weights sum to n_classes. This compensates for class imbalance (e.g., ubuntu-web-server at 1.7% of training data vs majority classes at 15%+).

Focal modulation (gamma=2.0) down-weights easy, well-classified examples and up-weights hard, confusable examples. This addresses class confusion (Windows variants with near-identical fingerprints) on top of class imbalance.

Previously (Run 1-3): nn.CrossEntropyLoss(weight=class_weights). Changed in Run 4 because weighted CE treats all predictions equally within a class -- the model was getting high reward for easy Mac/Ubuntu classifications while barely being penalized for confusing Windows variants.

### Training Observability

1. **Startup**: data pipeline timing, class distribution with percentages, batch counts, model build time, parameter count (quantum vs classical)
2. **Batch progress** (every 10 batches): running average loss, batch time, epoch ETA
3. **Gradient norms** (every 50 batches): quantum layer and classical head norms reported separately, CLIPPED flag when clipping activates
4. **Per-class F1** (every epoch): F1 for each class index, WARNING for any class with F1=0.0
5. **Timing** (every epoch): train vs validation time split
6. **Progress JSON** (atomic writes): training_progress.json in models/ for external monitoring via scripts/monitor.py

All output uses print(..., flush=True) for Docker log compatibility.

## Model Serialization

Two files per model:
- {name}.pt   -- PyTorch state dict (quantum + classical weights)
- {name}.json -- circuit config + preprocessing metadata (n_qubits, n_layers, n_features, n_classes, feature_indices, label_classes, backend)

JSON config is used by load_checkpoint() to reconstruct the model architecture before loading weights. This allows the test script to rebuild the exact model without knowing the original training arguments.

## Issues Encountered & Decisions

### Issue 1: PyTorch CUDA Driver Mismatch

**Problem**: The PennyLane Docker image (pennylaneai/pennylane:latest-lightning-gpu) ships PyTorch 2.11.0+cu130, compiled for CUDA 13.0. The host NVIDIA driver (570.211.01) only supports up to CUDA 12.8. Result: torch.cuda.is_available() = False. PyTorch's backward pass for the classical head falls back to CPU entirely.

**Key insight**: PennyLane's lightning.gpu backend has its own CUDA bindings separate from PyTorch, so the quantum circuit still runs on the GPU. Only PyTorch is affected. The quantum circuit forward/backward (adjoint differentiation) runs on GPU; the classical optimizer step and loss computation run on CPU.

**Decision**: Upgrade host NVIDIA driver from 570.211.01 to 590.48.01 (available in Ubuntu 24.04 repos). Driver 590 supports CUDA 13.x, which matches the container's PyTorch. Preferred over pinning PyTorch to cu128 because it keeps the full stack current.

**Status**: Driver 590.48.01 installed.

### Issue 2: Another GPU Workload Sharing the Card

**Problem**: Another Docker container (an LLM inference server) was consuming 22,126 MiB of the RTX 3090's 24,576 MiB VRAM, leaving only ~700 MiB for quantum training.

**Key insight**: nvidia-smi showed 91% GPU utilization, which was misleading — utilization measures "% of time a kernel is running," not throughput. The 20-qubit state vector is only ~16 MB, so VRAM was not the bottleneck. Training ran at 27s/batch regardless.

**Decision**: Stop other GPU workloads during training runs. While it didn't directly affect per-batch speed for this circuit size, sharing the GPU adds scheduling overhead and would matter for larger circuits.

### Issue 3: Training Speed — Batch Size Too Small

**Problem**: With batch_size=64 and 86,113 training samples, each epoch requires 1,346 batches. At ~27s/batch, one epoch takes ~10 hours. 50 epochs would take ~21 days.

**Root cause**: The quantum circuit processes samples sequentially (not batched at the GPU level). Each batch means 64 sequential circuit evaluations + 1 weight update. More batches = more overhead.

**Decision**: Increase batch_size from 64 to 512 (8x fewer batches per epoch: 1,346 -> 169).

**Why 512 and not 1024**:
- Quantum circuits process samples one at a time, so larger batches don't parallelize the forward pass
- 1024 requires more aggressive learning rate scaling, risking instability
- With 12 classes (some rare), 512 provides enough samples per batch for stable gradient estimates
- 512 is conservative enough to avoid LR tuning issues while still providing 8x speedup

### Issue 4: Linear LR Scaling Failed

**Problem**: The batch_size 64->512 change originally used the linear scaling rule (LR proportional to batch size: 0.01 -> 0.08). Val F1 oscillated wildly (0.29 -> 0.16 -> 0.30 -> 0.16).

**Root cause**: The linear scaling rule assumes gradient variance decreases proportionally with batch size. This holds for classical networks but not quantum circuits:
1. Quantum gradients from adjoint differentiation on a 2^20-dimensional state vector — small angle changes in RY/RZ gates can flip interference patterns
2. 160 variational parameters create a highly non-convex landscape with narrow valleys
3. With 12 classes and 15.5x class imbalance, inverse-frequency weighting amplifies rare-class gradients

**Decision**: Reverted LR to 0.01. Added LR warmup (3 epochs, linear ramp from lr/10 to lr), ReduceLROnPlateau scheduler (halve on 3-epoch stall), and gradient clipping (max_norm=1.0).

### Issue 5: DataLoader Not Parallelized

**Problem**: PyTorch DataLoader defaulted to num_workers=0 (single-threaded, blocking). GPU sits idle while the next batch is prepared.

**Decision**: Set num_workers=4 (train) / 2 (test), pin_memory=True, persistent_workers=True.

### Issue 6: tqdm Output Buffering in Docker

**Problem**: tqdm progress bars use \r (carriage return) for in-place updates. Docker containers run without a TTY, so tqdm output was garbled in docker logs.

**Decision**: Removed tqdm entirely. Replaced with plain batch logger printing every 10 batches to stdout with flush=True. Works correctly with Docker logs, tee, and tmux.

### Issue 7: Docker Build Context Too Large

**Problem**: Docker COPY . . copies the entire project directory (including 9GB of CSV data) into the build context.

**Recommendation**: Add data/*.csv to .dockerignore. Data should only be accessed via the volume mount.

### Issue 8: Insufficient Training Visibility

**Problem**: Only per-epoch loss and val_f1 were logged. No gradient norms, no per-class F1, no timing breakdown.

**Decision**: Added structured logging:
1. Startup: data pipeline timing, class distribution, parameter counts
2. Gradient norms every 50 batches (quantum vs classical, with CLIPPED flag)
3. Per-class F1 every epoch with WARNING for zero-F1 classes
4. Train vs validation timing split per epoch
5. Class weights at init with min/max/ratio
6. Progress JSON for external monitoring

### After Run 2 Analysis — Circuit Architecture + Optimizer Tuning (2026-04-21)

Run 2 regressed significantly from Run 1 (0.2946 vs 0.3483 F1) despite eliminating catastrophic collapses. Two categories of changes for Run 3: circuit architecture (expressivity) and hyperparameter tuning (optimizer).

#### Problem: Expressivity Ceiling

Both runs plateaued hard — Run 1 at loss ~1.535, Run 2 at ~1.50. The loss barely moved across many epochs despite healthy gradient norms on the classical side. This pattern points to an expressivity ceiling in the quantum circuit, not just an optimizer problem.

Root causes identified:

1. **Linear CNOT topology limits long-range correlations**: The nearest-neighbor chain (q0→q1→q2→...→q19) means features encoded on distant qubits (e.g., TTL bit at q0 and TCP window bit at q17) can only interact after information hops through the full chain. With 4 layers, correlations build slowly. For OS fingerprinting, feature correlations are global — TTL patterns need to interact directly with TCP option patterns.

2. **Single data encoding limits function class**: The circuit only sees the input features once at the start. After AngleEmbedding, the variational layers operate on a fixed encoded state. This limits the circuit to learning functions that are essentially first-order Fourier series of the input — only linear decision boundaries per layer. With 12 OS classes sharing similar binary feature patterns, linear boundaries are insufficient.

#### Decision: Star Topology Entanglement

Replace both CNOT blocks (post-encoding and per-layer) with star topology from q0:

Before: for i in range(n_qubits - 1): qml.CNOT(wires=[i, i + 1])
After:  for i in range(1, n_qubits): qml.CNOT(wires=[0, i])

q0 becomes a global control qubit — every other qubit gets directly entangled with it in one pass instead of hopping through the chain. Gate count stays identical (19 CNOTs), zero extra parameters. q0 carries ipv4_ttl_1 (MI=0.6773, the strongest feature), so making it the hub means every qubit gets direct entanglement with the most discriminative signal.

No Hadamard on q0 needed — that's only for GHZ state preparation from |0⟩. After AngleEmbedding, q0 is already rotated by the data, so the star CNOTs create entanglement directly.

Trade-off: qubits 1-19 no longer directly interact with each other (only through q0). With 4 layers of re-uploading this should propagate information sufficiently, but if mid-range features (tcp_opt bits at q3-q6) show F1 regression, this topology may need revisiting.

#### Decision: Data Re-uploading

Add AngleEmbedding at the start of each variational layer:

for layer in range(n_layers):
    qml.AngleEmbedding((inputs + 1) * np.pi / 2, wires=range(n_qubits), rotation="Y")  # re-upload
    for i in range(n_qubits):
        qml.RY(weights[layer, i, 0], wires=i)
        qml.RZ(weights[layer, i, 1], wires=i)
    for i in range(1, n_qubits):
        qml.CNOT(wires=[0, i])

This gives the circuit universal approximation capability (Pérez-Salinas et al., 2020). Each layer now sees the raw input features again, allowing the variational rotations to learn non-linear interactions with the data at each depth level. Zero extra trainable parameters — only adds 20 RY gates per layer (data-driven, not learned).

Combined with star topology, this means: every layer re-encodes the data, applies learned rotations, then entangles all qubits through q0. The circuit can now learn progressively more complex decision boundaries at each layer depth.

### After Run 3 Analysis — Architecture Overhaul for Class Confusion (2026-05-07)

Run 3 plateaued at val_F1=0.3510 with classes 8, 9, 11 (all Windows variants) at near-zero F1. Root cause: class confusion, not imbalance. Five changes for Run 4, all with approximately zero additional compute per batch:

#### Problem: Class Confusion

Classes 8 (windows-10-pro, 23.2%), 9 (windows-7-pro, 5.0%), and 11 (windows-vista, 3.6%) together represent 31.74% of training data but have F1 scores of 0.04, 0.05, and 0.01. The model cannot distinguish Windows variants with near-identical network fingerprints.

Evidence from training logs:
- Epoch 3: class 8 F1=0.52, class 7 F1=0.05 (model learned 8, forgot 7)
- Epoch 5: class 8 F1=0.00, class 7 F1=0.59 (swapped back)
- The model oscillates between Windows variants rather than learning to distinguish them

Five contributing factors:
1. Feature selection (mutual_info_classif) selects globally informative features, not features that distinguish similar classes
2. Star topology routes all entanglement through q0, preventing direct qubit-to-qubit correlations
3. PauliZ-only measurements extract only one axis of information per qubit
4. Weighted CrossEntropyLoss doesn't focus gradient signal on hard/confusable examples
5. Classical head (Linear(20,64)->ReLU->Linear(64,12)) lacks capacity for fine-grained boundaries

#### Decision 1: Ring Topology Entanglement (was Star)

Replace star CNOT (all through q0) with ring topology (nearest-neighbor + wrap-around):
  Before: for i in range(1, n_qubits): CNOT(0, i)
  After:  for i in range(n_qubits): CNOT(i, (i+1) % n_qubits)

Why: star topology means qubits 1-19 never directly interact. If features at qubit 8 and qubit 14 together distinguish windows-10-pro from windows-10, the star topology cannot learn that correlation. Ring allows nearest-neighbor correlations to propagate. Cost: +1 CNOT per layer (20 vs 19), essentially zero.

Rejected alternative: all-to-all entanglement (190 CNOTs per layer, ~2-3x training time).

#### Decision 2: Triple Pauli Measurements (PauliZ + PauliX + PauliY)

Measure all three Pauli observables on each qubit: 60 outputs instead of 20.

Why: PauliZ measures one "axis" of qubit information. Adding PauliX and PauliY extracts two additional orthogonal axes — 3x information with zero additional gate cost. The quantum state already contains this; we were not reading it.

#### Decision 3: Larger Classical Head with Dropout

  Before: Linear(20, 64) -> ReLU -> Linear(64, 12) = 2,124 params
  After:  Linear(60, 128) -> ReLU -> Dropout(0.3) -> Linear(128, 12) = 9,356 params

Why: with 60 inputs (from triple measurements) and 5 confusable Windows variants, the old head lacked capacity for fine decision boundaries. Dropout prevents overfitting. Cost: microseconds vs 251s quantum layer.

#### Decision 4: Focal Loss (was Weighted CrossEntropyLoss)

  FL(p_t) = -alpha_t * (1 - p_t)^gamma * log(p_t), gamma=2.0

Why: weighted CE treats all correct/incorrect predictions equally within a class. Focal loss down-weights easy, well-classified examples and up-weights hard, confusable examples. Forces gradient signal toward the Windows variants the model keeps confusing. Zero compute overhead.

#### Decision 5: ANOVA F-scores (was Mutual Information)

  Before: SelectKBest(mutual_info_classif, k=20)
  After:  SelectKBest(f_classif, k=20)

Why: mutual_info_classif computes global dependency, favoring features that separate distinct classes (Mac vs Ubuntu vs Windows). f_classif (ANOVA F-test) computes between-class vs within-class variance, which is inherently class-aware — features that differ across ANY class pair score highly, even subtle Windows variant differences. This is the most foundational change: if the 20 features don't distinguish Windows variants, no model improvement can compensate.

#### Changes NOT Made (and why)

1. More variational layers (4→6-8): ~50% more training time, barren plateau risk. Feature selection is the bottleneck, not circuit depth.
2. All-to-all CNOT: 190 CNOTs vs 20, ~2-3x batch time. Ring is sufficient.
3. Hierarchical classification: major architectural overhaul for uncertain gain. Try simpler fixes first.
4. More qubits (>20): exponential simulation cost. Not feasible on RTX 3090.
5. Stratified batch sampling: engineering complexity for uncertain gain. Focal loss achieves similar effect.

#### Issue 1: f_classif Selected Redundant Features

**Feature overlap: only 4 of 20 features shared** (ipv4_ttl_0, ipv4_ttl_1, tcp_opt_20, tcp_opt_40).

f_classif selected 14 features with nearly identical F-scores (~7856): tcp_opt_9 through tcp_opt_31. These are likely correlated TCP option bits carrying redundant information. The model effectively had 2 useful features (TTL bits) and 18 near-duplicates.

mutual_info_classif selected features with varied MI scores (0.28-0.68), including tcp_doff bits and a wider spread of tcp_opt bits (32-45), providing genuinely diverse signal across the TCP/IP stack.

The f_classif (ANOVA F-test) assumption was wrong: while F-scores are theoretically class-aware, in practice the binary nPrint features caused many TCP option bits to have degenerate F-scores because the between-class/within-class variance ratio is identical for correlated binary columns. mutual_info_classif handles correlated binary features better because it measures non-linear dependency.

#### Issue 2: Focal Loss Suppressed Early Learning

FocalLoss with gamma=2.0 down-weights all examples by (1-p_t)^2. At random initialization (p_t ≈ 1/12 ≈ 0.083), the focal weight is 0.84 — modest suppression. But the combined effect with class weights created a gradient-starved regime:

- Initial loss: 0.81 (vs 2.27-2.43 in Runs 1-3 with CrossEntropyLoss)
- Quantum gradient norms decayed from 0.033 to 0.008 in 4 epochs
- The circuit entered a barren plateau: gradients too small to escape the initial random parameter region
- CrossEntropyLoss provides full gradient signal, letting the quantum circuit learn broad class separations before fine-tuning. FocalLoss assumes the model already has a basic competence to build on — it cannot bootstrap from scratch.

#### Issue 3: Triple Pauli Measurements Cost 3x (Not Zero)

The pre-Run 4 analysis stated "zero additional gate cost" for triple Pauli measurements. This was true for gates but missed the adjoint differentiation cost:

- Each qml.expval() requires a separate backward pass through the circuit during adjoint differentiation
- 60 measurements (Z+X+Y) vs 20 (Z only) = 3x more adjoint passes
- Actual batch time: 699s vs ~251s expected = 2.8x slowdown
- This does not affect accuracy, but nearly triples training time per epoch

#### Decision: Revert Feature Selection and Loss, Keep Architecture (Run 5)

Reverted to mutual_info_classif and CrossEntropyLoss. Kept all architecture improvements: ring topology, data re-uploading, triple Pauli measurements (60 outputs), larger classical head (Linear(60,128)->ReLU->Dropout(0.3)->Linear(128,12)).

Rationale: the architecture changes (ring, triple Pauli, larger head) are theoretically sound and were not the cause of regression. The regression came from the feature and loss changes that starved the model of gradient signal. By keeping the architecture and fixing the inputs/optimizer, Run 5 tests whether ring topology + triple Pauli + larger head can surpass Run 3's 0.3510 F1.

### After Run 5 Analysis — Re-introducing Focal Loss (2026-05-22)

Run 5 confirmed that the architecture improvements (ring topology, triple Pauli, larger head) work well with mutual_info_classif features. The remaining problem is class confusion: windows-7-pro (0.03) and windows-vista (0.01) have near-zero F1, and windows-10 (0.08) trades off with windows-10-pro (0.52).

FocalLoss was incorrectly blamed for Run 4's failure. The post-mortem showed two simultaneous failures: f_classif selected 14 redundant features AND focal loss suppressed gradients. With good features now confirmed, FocalLoss can target the class confusion problem it was designed to solve.

#### Decision: Implement FocalLoss (CrossEntropyLoss → FocalLoss)

FL(p_t) = -alpha_t * (1 - p_t)^gamma * log(p_t), gamma=2.0

Combined with existing inverse-frequency class weights. The model now has basic competence (F1>0.32), so focal modulation will focus gradients on the hard Windows variant examples rather than starving them as in Run 4.
