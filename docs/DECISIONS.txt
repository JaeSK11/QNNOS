--------------------------------------------------------------------------------
PROBLEM DIAGNOSIS
--------------------------------------------------------------------------------

Root cause: CLASS CONFUSION, not class imbalance.

Classes 8, 9, 11 are NOT small classes:
  - Class 8 (windows-10-pro):  19,948 training samples (23.2%)  -- 2nd largest
  - Class 9 (windows-7-pro):    4,314 training samples (5.0%)
  - Class 11 (windows-vista):   3,127 training samples (3.6%)
  - Combined: 31.74% of all training data

These are all Windows variants with near-identical network fingerprints. The
model was collapsing them into a single decision region -- when it learned to
classify one Windows variant, it forgot another (epochs 3-5 showed class 7 and
class 8 trading off F1 scores).

Evidence:
  - Epoch 3: class 8 F1=0.52, class 7 F1=0.05 (swapped)
  - Epoch 5: class 8 F1=0.00, class 7 F1=0.59 (swapped back)
  - Epoch 26: class 7 F1=0.59, class 8 F1=0.04 (settled on class 7)

Contributing factors:
  1. Feature selection discarding class-discriminative features
  2. Quantum circuit bottleneck limiting information extraction
  3. Undersized classical head lacking capacity for fine boundaries
  4. Loss function not penalizing hard/confusable examples enough

--------------------------------------------------------------------------------
DECISION 1: Ring Topology Entanglement (was Star)
--------------------------------------------------------------------------------

File changed: circuits/model.py

Before:
  Star topology -- all CNOTs route through qubit 0.
  Qubits 1-19 never directly interact with each other.

After:
  Ring topology -- each qubit entangles with its neighbor, wrap-around.
  CNOT(i, (i+1) % n_qubits) for all i.

Why:
  If features at qubit 8 and qubit 14 together distinguish windows-10-pro from
  windows-10, the star topology cannot learn that correlation -- it must route
  everything through qubit 0 as a bottleneck. Ring topology allows nearest-
  neighbor correlations to propagate and costs only 1 extra CNOT per layer
  (20 vs 19). Essentially zero additional compute.

What we considered but rejected:
  - All-to-all entanglement: 190 CNOTs per layer vs 20. Would roughly 2-3x
    training time per batch (currently 251s/batch, would become ~500-750s).
    Not worth the compute cost when the input features may not even contain
    the right discriminative information yet.

--------------------------------------------------------------------------------
DECISION 2: Triple Pauli Measurements (PauliZ + PauliX + PauliY)
--------------------------------------------------------------------------------

File changed: circuits/model.py

Before:
  20 PauliZ measurements only (one per qubit).

After:
  60 measurements total: PauliZ, PauliX, PauliY on each of 20 qubits.

Why:
  PauliZ measures one "axis" of information per qubit. Adding PauliX and PauliY
  extracts two additional orthogonal axes -- 3x the information from the same
  circuit with zero additional gate cost. No extra qubits, no extra depth, no
  extra simulation time. The quantum state already contains this information;
  we were simply not reading it.

  This directly addresses the information bottleneck: the circuit compresses
  2^20 (~1M) dimensional Hilbert space down to measurements. Going from 20 to
  60 outputs gives the classical head 3x more signal to work with.

Impact on model:
  - Quantum output dimension: 20 -> 60
  - Classical head input: 20 -> 60
  - Quantum parameters unchanged: 160
  - No change to training time per batch

--------------------------------------------------------------------------------
DECISION 3: Larger Classical Head with Dropout
--------------------------------------------------------------------------------

File changed: training/hybrid_model.py

Before:
  Linear(20, 64) -> ReLU -> Linear(64, 12)
  Parameters: 2,124

After:
  Linear(60, 128) -> ReLU -> Dropout(0.3) -> Linear(128, 12)
  Parameters: 9,356 (7,808 + 1,548)

Why:
  The old head had to separate 12 classes (including 5 confusable Windows
  variants) from only 20 coarse quantum features through a 64-neuron hidden
  layer. This is insufficient capacity for fine-grained decision boundaries.

  With 60 inputs (from triple measurements) and 128 hidden neurons, the head
  has ~4x more capacity to learn the subtle differences between Windows
  variants. Dropout (0.3) prevents overfitting to the larger head.

  The quantum layer at 251s/batch is the compute bottleneck. The classical
  head adds microseconds. This change is effectively free.

What we considered but rejected:
  - Even larger heads (256+ neurons): Diminishing returns. The bottleneck is
    still the quantum feature quality, not classical capacity.
  - Batch normalization: Adds complexity; dropout alone should suffice given
    the binary nature of the input features. (Superseded: the inputs are
    ternary, Decision 6, and --batchnorm is on in the production model.)

--------------------------------------------------------------------------------
DECISION 4: Focal Loss (was Weighted CrossEntropyLoss)
--------------------------------------------------------------------------------

File changed: training/trainer.py, config/defaults.py

Before:
  nn.CrossEntropyLoss(weight=class_weights)
  Inverse-frequency weighting: weight[i] = (1/count[i]) / sum(1/count) * 12

After:
  FocalLoss(weight=class_weights, gamma=2.0)
  FL(p_t) = -alpha_t * (1 - p_t)^gamma * log(p_t)

Why:
  Weighted CE treats all correct/incorrect predictions equally within a class.
  The model was getting high reward for correctly classifying easy Mac/Ubuntu
  samples (class 0: F1=0.86) while barely being penalized for misclassifying
  confusable Windows variants.

  Focal loss with gamma=2.0 down-weights easy, well-classified examples
  (where p_t is high) and up-weights hard, confusable examples (where p_t is
  low). This forces the model to focus gradient signal on the Windows variants
  it keeps confusing, rather than coasting on easy classifications.

  Combined with the existing inverse-frequency class weights, this addresses
  both class imbalance (via alpha weights) and class confusion (via focal
  modulation).

  Zero computational overhead -- same forward/backward pass cost.

Why gamma=2.0:
  This is the standard value from the original focal loss paper (Lin et al.,
  2017). It provides strong down-weighting of easy examples without being so
  aggressive that it destabilizes training. Can be tuned later if needed.

--------------------------------------------------------------------------------
DECISION 5: ANOVA F-scores (was Mutual Information)
--------------------------------------------------------------------------------

File changed: data/pipeline.py

Before:
  SelectKBest(mutual_info_classif, k=20)

After:
  SelectKBest(f_classif, k=20)

Why:
  mutual_info_classif computes a global measure of dependency between each
  feature and the label. It tends to select features that separate the most
  distinct classes (Mac vs Ubuntu vs Windows) but not features that distinguish
  similar classes within a group (windows-10 vs windows-10-pro).

  f_classif (ANOVA F-test) computes the ratio of between-class variance to
  within-class variance for each feature. This is inherently class-aware:
  features that have different distributions across ANY pair of classes will
  score highly, even if the difference is subtle (e.g., a TCP option that
  differs between Windows 7 and Windows 10 but is the same for all Ubuntu
  variants).

  This is the most impactful change. If the 20 selected features don't contain
  information that distinguishes Windows variants, no amount of circuit or
  model improvement can compensate. Garbage in, garbage out.

  No computational overhead -- feature selection runs once before training.

What we considered but rejected:
  - Increasing k from 20 to 40-50: Would require more qubits, which
    exponentially increases quantum simulation cost. Not feasible on current
    hardware without a circuit redesign.
  - Per-class feature selection: More complex to implement and would require
    different features per classification stage. Saved for future work if
    ANOVA alone doesn't resolve the confusion.

--------------------------------------------------------------------------------
CHANGES NOT MADE (and why)
--------------------------------------------------------------------------------

1. More variational layers (4 -> 6-8):
   Would increase training time ~50% per epoch. Risk of barren plateaus
   (vanishing gradients in deep quantum circuits). Diminishing returns given
   the current feature selection is the primary bottleneck.

2. All-to-all CNOT entanglement:
   190 CNOTs per layer vs 20. Would roughly 2-3x batch time. The ring
   topology provides a good balance of expressivity and efficiency.

3. Hierarchical classification (OS family -> variant):
   Significant architectural overhaul. Requires two models or a two-stage
   circuit, new training logic, and pipeline changes. Saved for future work
   if the current changes don't resolve class confusion.

4. Increasing qubit count beyond 20:
   Exponential simulation cost. 20 qubits on lightning.gpu is already near
   the practical limit for reasonable training times on RTX 3090.

5. Stratified batch sampling:
   Would ensure confusable class pairs co-occur in each batch. Added
   engineering complexity for uncertain gain. Focal loss achieves a similar
   effect by focusing gradients on hard examples regardless of batch
   composition.

DECISION 6: Ternary-Aware Encoding RY((x+1) * pi/2)  (was RY(x * pi))
--------------------------------------------------------------------------------

File changed: circuits/model.py (both AngleEmbedding calls: initial encoding
and the per-layer data re-uploading)

Before:
  qml.AngleEmbedding(inputs * np.pi, rotation="Y")
  Mapping: 0 -> RY(0) = |0>,  1 -> RY(pi) = |1>,  -1 -> RY(-pi) = -|1>

After:
  qml.AngleEmbedding((inputs + 1) * (np.pi / 2), rotation="Y")
  Mapping: -1 -> RY(0) = |0>,  0 -> RY(pi/2) = equator,  1 -> RY(pi) = |1>

Why (the bug):
  RY(-pi) = -RY(pi) as operators — they differ only by a scalar -1, i.e. a
  global phase. So under the old encoding, "field absent" (-1) and "bit set"
  (+1) entered the circuit as PHYSICALLY IDENTICAL states. No downstream gate
  or measurement can recover the difference. Crucially, data re-uploading does
  NOT rescue this: the re-uploaded RY(x*pi) hits an entangled state, but the
  scalar still factors out of the whole state, layer after layer.

  Verified numerically on the real circuit (20 qubits, 4 layers, cnot
  entangler): flipping 7 features from -1 to +1 changed all 60 expectation
  values by at most 6e-8 (float noise). Regression test added:
  tests/test_circuits.py::test_circuit_ternary_encoding_distinguishes_absent_from_set

  Consequence of the bug: the quantum circuit only ever saw {0} vs {1,-1} —
  a lossy binarization where "TCP option bit set" and "no TCP options at all"
  were the same value. With --skip enabled, the raw features (including -1s)
  bypass the circuit into the classical head, so any absent-vs-set signal was
  being learned entirely classically.

Why this fix (vs alternatives):
  - Remapping -1 -> 0 in the pipeline: simplest, but merely chooses a
    different collision (absent aliases with 0 instead of with 1).
  - Presence qubits (one per field): doubles qubit count; infeasible at the
    24 GB VRAM ceiling.
  - The affine map keeps one qubit per feature, costs zero extra gates or
    parameters, and gives all three values distinct Bloch latitudes.

Side effects to be aware of:
  1. The post-encoding state is no longer a computational basis state
     (0-valued features sit on the equator), so the FIRST CNOT ring now
     genuinely entangles. The old "the first ring is just classical XOR"
     description no longer holds. This also means the "crz" entangler now has
     something to bite on from layer 0.
  2. NOT weight-compatible in spirit with checkpoints trained under the old
     encoding: shapes are unchanged, but the input-to-state mapping differs,
     so resuming an old run under the new encoding mixes two incompatible
     regimes. Requires a fresh training run (archive the old model_out).
  3. Encoding now uses 3 points per qubit instead of 2, which also softens
     the "binary features use only 2 Bloch points" limitation.

--------------------------------------------------------------------------------
PROBLEM DIAGNOSIS (speed) + a correction to earlier assumptions
--------------------------------------------------------------------------------

Symptom: ~40h/epoch, ~1.35s/sample fwd+bwd on lightning.gpu (BATCH_SIZE=512,
60 observables, adjoint differentiation).

Root cause: diff_method="adjoint" cost scales LINEARLY with the number of
measured observables. Isolation benchmarks (lightning.qubit CPU, one sample):
  - forward, weights NOT requiring grad:  0.23 s/sample
  - the moment weights require grad:      21.8 s/sample  (~93x)
  - forward == forward+backward           => the whole cost is the adjoint
    Jacobian, computed EAGERLY on the forward pass; torch.no_grad() does not
    suppress it.
The 60-observable measurement (Decision 2) is what makes that Jacobian
expensive: adjoint re-does its reverse sweep per observable.

  ** This corrects Decision 2's premise. ** Decision 2 ("Triple Pauli
  Measurements") stated 20->60 outputs had "zero additional gate cost ... No
  change to training time per batch." That is true for a pure forward pass, but
  FALSE under adjoint differentiation, where training cost is ~proportional to
  observable count. Measured on lightning.gpu: 60 obs = 1.35 s/sample (~32h/
  epoch) vs 20 obs (PauliZ only) = 0.49 s/sample (~11.7h/epoch), a 2.75x
  difference from the measurement count alone.

Also corrected: a mid-investigation arithmetic error assumed BATCH_SIZE=64 and
briefly mis-stated per-sample cost as ~11s. The real BATCH_SIZE is 512
(config/defaults.py), so lightning.gpu is ~1.35 s/sample, and CPU/backprop
"fixes" first benchmarked on lightning.qubit were actually SLOWER than the GPU
baseline. Always benchmark on the device training actually uses (lightning.gpu).

Dead end recorded: default.qubit + diff_method="backprop" would make cost
observable-count-INDEPENDENT and would be ideal for high-parameter circuits, but
it is CPU-bound here. On PennyLane 0.45, default.qubit allocates its statevector
on CPU, so batched GPU execution dies with "Expected all tensors on the same
device, cuda:0 and cpu" inside _prepare_batched_params. GPU backprop is
therefore unavailable without patching PennyLane internals; adjoint on
lightning.gpu remains the only practical trainer.

PROBLEM DIAGNOSIS (accuracy) -- confusion structure of the plateau
--------------------------------------------------------------------------------

Confusion matrix of the epoch-4 checkpoint (stratified 15/class val
subsample): the model is effectively a 3-way OS-FAMILY
classifier with near-zero cross-family leakage.
  - macOS: cleanly separated (13/15, precision 1.00) -- the only class that works.
  - ALL Windows versions collapse into windows-10-pro (a sink: recall 1.00,
    precision 0.23). windows-10 -- the largest class (27%) -- scores F1 0.00.
  - Ubuntu rows churn among Ubuntu columns (random within-family) but never
    cross into Windows/macOS.
Conclusion: cross-family separation is ~perfect; within-family VERSION
discrimination is ~random. The entire 12-class deficit is within-family (esp.
windows-10 vs windows-10-pro). This matches the 2026-05-07 diagnosis but with a
full matrix confirming the collapse direction. Dropping macOS would NOT help (it
is the one class that works) and would only lower macro-F1.

DECISION 7: "ring_long" entangler -- ring + long-range CNOT shortcuts
            (rejects full all-to-all on MEASURED cost)
--------------------------------------------------------------------------------

Files changed: circuits/model.py (new "ring_long" branch + _entangle helper),
config/defaults.py (SHORTCUT_OFFSETS), scripts/train.py (--entangler ring_long,
--shortcut-offsets), training/hybrid_model.py, training/trainer.py.

What: in addition to the nearest-neighbor ring, add a fixed CNOT between qubits
i and (i+k) % N for each offset k in SHORTCUT_OFFSETS (default [5, 10]), every
layer. Offset 10 = antipodal on 20 qubits; offset 5 = quarter-way. This shrinks
the ring's graph diameter so distant feature-bits can correlate within a few
layers instead of propagating all the way around the ring.

Why: the confusion diagnosis says the missing capability is reachability between
distant qubits whose bits jointly distinguish same-family versions. The ring
(Decision 1) only correlates neighbors. Long-range shortcuts add that
reachability. Fixed CNOTs => ZERO extra parameters (weight_shapes identical to
"cnot", (n_layers, n_qubits, 2)) => no added barren-plateau risk from parameter
count.

What we considered but rejected (now with MEASURED numbers, superseding the
2026-05-07 estimate in Decision 1 / "Changes not made #2"):
  - Full all-to-all (190 CRZ pairs/layer, trainable): measured 4.94 s/sample on
    lightning.gpu adjoint = ~118 h/epoch (~5 DAYS per epoch). Adjoint scales with
    the 760 coupling parameters; backprop (which would not) is GPU-blocked (see
    above). Impractical -- you cannot complete even one epoch to evaluate it.
  - Trainable CRZ ring ("crz", Decision-era option): tunes entanglement STRENGTH
    on the existing neighbor links but adds no new links, so it cannot reach
    distant bits; also adds params/plateau risk. Deferred as a later A/B.
  - ring_long [5,10] measured at 0.59 s/sample (Z-only) = ~14 h/epoch: it buys
    the reachability at ~1/8th of all-to-all's gate cost and stays trainable.

DECISION 8: Drop to 20 observables (PauliZ only)  -- partially reverses Decision 2
--------------------------------------------------------------------------------

Files changed: config/defaults.py (MEASURE_AXES), circuits/model.py
(configurable measurement axes), training/hybrid_model.py (head input dim now
len(measure_axes)*n_qubits, was hardcoded 3*n_qubits), scripts/train.py
(--measure-axes), training/trainer.py (load_checkpoint restores saved axes).

What: measure only PauliZ per qubit (20 outputs) instead of PauliZ+PauliX+PauliY
(60). MEASURE_AXES is configurable and DEFAULTS to ["Z","X","Y"] so pre-existing
checkpoints (which omit the key) rebuild to the identical 60-observable model.

Why: per the speed diagnosis, adjoint training cost is ~proportional to

GPU: ~2.75x faster (32h -> 11.7h/epoch for the ring; ~14h/epoch combined with
ring_long's extra gates). Decision 2's information-extraction argument still
holds for a pure forward pass, but the X/Y axes were not earning their ~2x
training-time cost given the model's already-weak within-family signal. If a
future run shows X/Y materially help accuracy, MEASURE_AXES can restore them.

DECISION 9: XGBoost gain-ranked feature basis (was SelectKBest mutual info)
--------------------------------------------------------------------------------

Date: 2026-07-27.  Files changed: docker-compose.yml (command), data/pipeline.py
(feature_names_to_indices), scripts/train.py (--feature-names); pipeline's
SelectKBest path kept as the default when no names are given.

What: model_xgb20 selects its 20 qubit features from an explicit list
(--feature-names): the top-20 features by gain from an XGBoost classifier fit
on the same data with the identifier columns removed, in rank order, instead
of SelectKBest(mutual_info_classif).

Why: mutual information ranks each feature independently (univariate), so it
never credits a feature for being useful IN COMBINATION. XGBoost gain ranks
features by how much they actually improved a strong supervised model's splits
on the same 783-column leak-free basis. The gain ranking surfaced tcp_wsize_*
window-size bits and control-flag bits (tcp_ackf_0, tcp_syn_0, tcp_rst_0) that
the MI ranking missed. A new model name (model_xgb20, not model_ringlong) keeps
--resume a safe no-op on first launch since the feature basis is not
weight-compatible.

Verified 2026-08-29: the stored feature_indices resolve to exactly the ranked
top-20, in order, 20/20, on the identical 783-column removal basis.

  - trainer's logged "Val_F1" is WEIGHTED F1; the XGBoost baseline logs MACRO. Mixed-up
